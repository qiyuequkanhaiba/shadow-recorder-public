# F2 修复前

## 显示器

2026-10-31，Windows 11 虚拟机（Parallels）里 Electron `screen.getAllDisplays()` 只有一块屏：

```
count=1
id=3544965526 bounds=0,0,1199,770 work=0,0,1199,722 scaleFactor=1
```

`prlctl` 不能给这台虚拟机加第二块屏。左 1920×1080 100% 加右 2560×1600 150% 没有在这里出现。

F1 的 `[screenshot-overlay] diagnostics` 只在打开选区时打印每块屏的 bounds 和窗口 bounds。它不记录 `mousemove`，所以不能用那条日志回答“拖出窗口后还能不能收到移动”。

## 同一块屏上的两个窗口

用两个相邻的顶层窗口代替两块屏，只看 Chromium 按住鼠标时的指针捕获。左窗口内容宽 344。在左窗口按下，拖到右窗口：

- 松开之前，移动事件只出现在左窗口。右窗口没有 `mousemove`。
- 左窗口的 `clientX` 从 132 增加到 580，大于内容宽度 344。`buttons` 一直是 1。
- 松开之后，右窗口才收到一次 `buttons` 为 0 的 `mousemove`。

日志在 `task-reports/f2/f2-pointer.log`。这是同一块屏上的两个窗口，不是两块不同缩放的屏。

## 代码里能确定的事

区域拖选没有 `setPointerCapture`。按下后如果系统把指针捕获留在起点窗口，`mousemove` 的 `clientX` 可以超出该窗口。现有 `confirmAreaSelection` 仍用起点窗口的 `scaleFactor` 把这个本地矩形换成物理像素，所以拖到另一块缩放不同的屏时，终点会按错的比例计算。

悬停高亮在 `screenshot-session.ts` 里对原生窗口的两个角分别调用 `screen.screenToDipPoint`。窗口横跨两块缩放不同的屏时，这两个角不在同一套 DIP 上，宽高会错。

## 物理机还要确认的点

- 左屏按下并拖进右屏时，左屏选区窗口是否仍收到 `mousemove`，以及 `clientX` 是否大于该窗口宽度。
- 松开后的图是否覆盖两块屏上的选区，像素是否是物理分辨率，而不是被 150% 放大或裁掉。
- 标注条是否出现在选区面积更大的那块屏上，图缩小后保存的仍是原图像素。
- 只在一块屏里拖、点选悬停窗口、3 秒倒计时、钉图，是否和现在一样。
- 不在录制时，选区是否仍不挡住远程桌面的抓屏。正在录制且“截图界面不进录像”打开时，选区是否仍被排除。
