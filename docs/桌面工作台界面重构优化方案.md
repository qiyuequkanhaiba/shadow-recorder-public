> 文档版本: v0.5  
> 状态: **可作为实施依据，可按 P0 开始**  
> 日期: 2026-11-12  
> 修订: v0.3 补齐配置提交信号、工作台加载现况和阶段合计。v0.4 修正回调的透传范围和对外工期。v0.5 结合全仓源码复核，补齐批量删除 `skipped` 状态恢复、空配置基线初始化与联动字段计数、P3 六类设置完整范围、旧 CSS 焦点/标签规则排除、以及 P6 门禁脚本顺序与浮窗色值断言。  
> 适用范围: `examples/desktop` 的 React 渲染界面，以及悬浮岛、截图覆盖层的界面颜色  
> 不适用范围: 录制内核、IPC、preload 的方法签名、`src-react/lib/`、`types/`。`src-react/hooks/` 只允许第 8 节列出的四个配置 hook 透传可选回调，以及 `useRecorderDashboardSnapshot.ts` 修复批量删除 `skipped` 恢复时的签名缓存问题  
> 依据: 对照当前仓库核对过的界面评审，以及 2026-11-11 至 2026-11-12 对 v0.1–v0.4 的源码复核。

## 1. 结论

只重做渲染界面。录制、导出、配置保存和桥方法的参数形状保持不变。

完成时先看行为、可访问性和视觉验收，再看体量。体量是维护目标，不是唯一门槛。

行为与可访问性必须通过：

1. 第 10 节的用户动作测试，覆盖调用次数、会话 ID、毫秒时间范围、取消和失败反馈。
2. 第 11 节的键盘、焦点、1080×760、深浅主题、Windows 125% / 150%、长文本、固定保存栏和减少动画。
3. 两套播放器在收工时都覆盖第 6 节的状态。P0 只锁源码里已经存在的行为。工作台的数据加载提示是 P5 的新增行为，不计入 P0 的现况。

体量目标：

1. `examples/desktop/src-react` 的 CSS 争取收到 5,000 行以内。超过时要说明剩余行来自哪一个仍在使用的页面，不能靠这条单独宣布完成。
2. `!important` 只允许出现在 `@media (prefers-reduced-motion: reduce)` 里，用来关掉动画。其余为 0。
3. `src-react` 里 token 文件以外的颜色为 0，包含 `#`、`rgb()`、`rgba()`、`hsl()`、`hsla()`。截图标注色不在这份检查里，规则见第 9 节。
4. 新界面文件争取不超过 500 行。超过时拆分，不把超行数本身当成可以跳过行为验收的理由。

阶段表合计 **32–39 个工作日（约 6.4–7.8 周）**，已经包含各阶段清单里的 Windows 冒烟。返修另计约 1 周，合计 **37–44 个工作日（约 7.4–8.8 周）**。对外按 **8–9 周**排期。P5 的 8–10 天约占阶段表 32–39 天的三成。不再使用 28–34 天、6 周或 7–8 周这些旧口径。

P0 到 P4 按顺序做。P5 在回顾页播放器的状态测试和换皮都通过后单独开工。P6 只依赖新 token 的生成脚本。P7 最后做。

## 4. 已拍板的做法

| 议题 | 决定 |
|---|---|
| 改动边界 | 只动渲染层。不改 `lib/`、`types/`、`preload.ts` 的方法签名，以及 `src-electron/modules/reqcase-shadow-recorder/`。`hooks/` 只允许第 8 节的四个文件透传 `onConfigCommitted`，以及 `useRecorderDashboardSnapshot.ts` 修复批量删除 `skipped` 恢复 |
| 播放计算 | 继续调用 `playback-review.ts`、`export-range.ts`、`studio-segment-window.ts` |
| 样式技术 | CSS Modules + CSS 变量。不使用 emotion、styled-components、Tailwind，也不把旧 CSS 放进 `@layer` |
| 旧样式退出 | 旧文件可以留到 P7 再删。旧规则对新页面的影响在该页迁移的同一次提交里解除 |
| 组件库 | 安装 `lucide-react`。行为测试安装 `@testing-library/react`、`@testing-library/user-event`、`jsdom`。这一轮不安装 Radix Dialog |
| 两套播放器 | 工作台和回顾页各留各的时间模型。只共用视频元素控制 |
| 播放器失败 | 工作台已有加载失败。回顾页目前没有，P4 换皮前补上并测试 |
| 悬浮岛 | 不改尺寸和弹簧。P6 只替换界面颜色，保留透明窗口防闪烁的 `color-scheme: only light` |
| 截图标注 | 红、黄、绿、蓝、白是用户画进图片的颜色，不随主题变化 |
| 时间轴 | 保留实测宽度与 `ContinuousPlaybackSegment` 类型导出。P5 还要用缩放、拖动和选区验证几何，不能只保留函数调用 |
| 护栏 | 测真实调用和参数。不测源码里有没有同名字符串 |
| 删除交互 | 改为选择模式。补充筛选、退出和部分失败规则，修复乐观删除后 `skipped` 恢复时的签名缓存失效问题 |
| 未挂载组件 | 删除 `RecorderSessionTimelinePanel.tsx` 和 `EvidenceExportPanel.tsx`，并同步测试、`historical-session-ui-smoke.mjs` 与 `examples/desktop/README.md` |
| 配置基线 | 放在常驻的 `RecorderPage`。启动时由 `hydrateTuningFromSettings`（含空配置）及失败回退初始化；运行期只有 bridge 的 `setConfig` 成功才更新，信号来自第 8 节的可选回调 |

`@layer` 仍不用于迁移。现有 CSS 没有分层，且有 868 处 `!important`。放进 layer 的 `!important` 会压过后面的新样式。

Radix Dialog 这一轮不用。它依赖的滚动锁定会插入 `<style>`，生产 CSP 会拦截，开发服务器看不出来。

回顾页现有空状态文案是：

- 正在录制或暂停：「正在写入当前切片，已封口的片段将在此就绪。」
- 其他：「当前会话没有可播放的视频切片。」

这两句和工作台的「暂无可回放录像」不是同一条路径。P0 的合同测试要分别断言，不能用一次全局字符串搜索代替。

P0 只测试现在已经存在的行为，并以此作为「先变绿、再改产品代码」的范围。工作台没有五种现成状态。`useRecorderDashboardSnapshot` 有 `loading`，但 `RecorderPage` 没有把它传给 `RecorderPlaybackStage`。工作台文案「正在写入当前切片」出现在 `isRecording && !isPaused`，表示正在录，不是数据请求未完成。

|---|---|---|---|
| 数据加载中 | 不存在。P0 断言没有这个提示 | 已有「正在读取录像切片…」 | 工作台在 P5 新增。规则见下 |

| 加载失败 | `onError` 后「当前录像加载失败」 | 视频元素没有 `onError`。P0 断言这个事实 | P4 换皮前补上，并改测试 |

| 清除失败 | `onLoadedMetadata` 会清掉播放错误；进入录制写入中也会清掉 | 没有失败状态，P0 不要求清除 | 回顾页在补上 `onError` 的同一提交里，切换片段并成功加载后清除 |

工作台数据加载提示是新增工作，放在 P5，不放进 P0：

- 首次加载：当前会话还没有片段列表，且 `dashboard.loading === true` 时，显示加载提示，不显示空状态，也不显示失败。

P4 改回顾页视觉之前，先补该页的 `onError`。没有这条失败测试之前，不开始回顾页换皮。P5 改工作台之前，先把上表的数据加载用例改成新期望，再写提示。不允许只改期望、不补行为。

演示桥指向不存在的 `/demo-segment.mp4`。浏览器里工作台的红框是加载失败，不是空状态。

共用的视频控制放到 `src-react/features/player/useVideoElementController.ts`，只含播放、暂停、按秒跳转、倍速、静音、全屏和上述互斥状态。连续时间轴留在工作台，片段序号留在 `HistorySessionPanel.tsx`。P4 可以先让回顾页用这个 hook。P5 再让工作台用它。计算仍调用现有 `lib/`。

## 7. 目录、样式退出和视觉

新代码只加这些位置，不搬 `hooks/`、`lib/` 现有文件：

```text
examples/desktop/src-react/ui/
examples/desktop/src-react/app/
examples/desktop/src-react/features/player/
examples/desktop/src-react/features/settings/
examples/desktop/src-react/features/privacy/
examples/desktop/src-react/features/evidence/
examples/desktop/scripts/ui-behavior/
examples/desktop/src-electron/generated/
```

P1 保持 `src-react/styles.css` 现有的 `@import` 顺序。新 token 由 `main.tsx` 在旧样式之后引入。

每个已迁移区域的根节点带 `data-ui-scope`，取值依次为 `shell`、`settings`、`review`、`workbench`。同一提交里，旧的元素选择器排除这个区域。Electron 37 支持复杂选择器，写成：

```css
button:where(:not([data-ui-scope] *))
```

`components.css` 里的 `input`、`select`、`textarea` 及其 `:hover`、`:focus`（即 `input:where(:not([data-ui-scope] *)):focus` 等）同样处理，防止鼠标点击新输入框时触发全局 `:focus` 漏出旧样式。只排除已经迁移的区域，旧页面继续吃原来的全局规则。

新组件的模块样式必须自己写全默认、`:hover`、`:focus-visible` 和 `:disabled`。检查时看计算后的背景、边框、最小高度和圆角，确认没有漏出 `components.css` 的渐变胶囊，也没有漏出 `button:hover:not(:disabled)` 的亮度滤镜。

各阶段退出的旧容器：

## 8. 配置基线

未保存项数只比较 `RecorderConfigPayload`。`autoApplyLastRecommendedProfile` 走 `setSettings`，不计入这个数字。

基线放在 `RecorderPage`，和现有的 `config` 并列。设置页用 `{activeTab === 'settings' ? ...}` 条件渲染，切走标签会卸载 `SettingsWorkspace`。基线若放在设置面板里，切回来会丢。

叶子路径比较与归一化规则：

1. **剔除 `undefined` 键**：比较前先递归剔除值为 `undefined` 的对象属性（如清空快捷键时写入 `{ shortcutStartRecording: undefined }`），避免与缺省键产生假阳性差异。
2. **忽略内部联动派生字段**：单次控件操作同时联动改写内部派生键时，只按主字段计数，忽略自动派生的伴随字段（包括随 `recordingWindowSeconds` 派生的 `segmentDurationSeconds` 和 `maxSteps`、随 `targetCaptureMode` 联动清空/同步的 `targetDisplayId` / `targetDisplayIds`、以及与 `semanticRecordingEnabled` 同步写入的 `defectEvidenceEnabled`）。
3. **复合规则计数**：`maskRegions` 新增或修改固定遮罩时，按实际修改的坐标字段或单条遮罩规则计数，避免从空数组 `[]` 填入单个坐标时因补齐默认 `{ x, y, width, height, label }` 膨胀为 5 项未保存。
4. **稳定比较**：其余对象和数组展开后每个值不同的叶子算 1 项，键顺序不影响计数，使用结构化克隆后的稳定序列化，不用对象引用相等。

| 事件 | 基线怎么变 |
|---|---|
| 启动后 `useRecorderBootstrap` 完成初始化 | 在传给 `useRecorderBootstrap` 的 `hydrateTuningFromSettings(settings)` 包装回调里将基线初始化为 `{ ...DEFAULT_CONFIG, ...(settings?.config ?? {}) }`（覆盖首次启动 `settings.config` 为 `undefined` 且 `applyRecorderBootstrapSnapshot` 不调用 `setConfig` 的情形）；若启动拉取异常失败，在错误处理分支回退为 `DEFAULT_CONFIG`。初始化完成前不显示未保存 |
| 用户改表单，只调用 `setConfig` | 基线不动 |
| `handleApplyConfig` 进入 `status: 'success'` | 只显示成功反馈，不在这里改基线。基线已经由 `applyConfig` 里的回调更新 |
| `handleApplyConfig` 进入 `catch` | 回调没有发生，基线不动，保留现有错误文案。`await` 正常结束不代表成功，因为函数捕获错误后仍返回 `Promise<void>` |
| `onConfigCommitted` 被调用 | 基线设为回调参数的结构化克隆 |
| `start()` 在 `setConfig` 之后失败 | 回调已经发生，基线不回滚。页面仍看到 `startRecording()` 拒绝 |
| `setSettings` 在 `applyProfile` 的 `setConfig` 之后失败 | 回调已经发生，基线不回滚。错误仍走现有 `onError` |
| `setConfig` 本身拒绝 | 不调用回调，基线不动 |
| 放弃 | 把 `config` 设回基线，不调用 bridge |
| 切换标签 | `config` 和基线都留在 `RecorderPage`，数字不变 |

现有接口给不出「配置已提交、但后一步失败」这个信号，所以允许一处范围例外，不再另写一套状态确认：

- 允许这四个 hook 增加并透传同一个可选回调：`useRecorderRuntime.ts`、`useRecorderRuntimeCommands.ts`、`useTuningAdvisor.ts`、`useTuningAdvisorCommands.ts`。页面现在是 `useRecorderRuntime(createRecorderRuntimeInput(...))` 和 `useTuningAdvisor(createTuningAdvisorInput(...))`。只改下面两个命令 hook 时，回调到不了页面。
- 四个输入类型各增加可选字段 `onConfigCommitted?: (committed: RecorderConfigPayload) => void`。`useRecorderRuntime` 把它传给 `useRecorderRuntimeCommands`，`useTuningAdvisor` 把它传给 `useTuningAdvisorCommands`。
- 不改 `lib/recorder-page-bindings.ts`。`createRecorderRuntimeInput` 和 `createTuningAdvisorInput` 的参数与返回值保持原样。页面在返回值之外追加回调，例如 `useRecorderRuntime({ ...createRecorderRuntimeInput(...), onConfigCommitted })`。`useTuningAdvisor` 同样处理。
- `applyConfig` 在 `await setConfig(input.config)` 成功后立即调用回调，参数是当时的 `input.config`。
- `startRecording` 在同样的位置调用回调，并且必须在 `start()` 之前。参数同样是当时的 `input.config`。
- `applyProfile` 仍先 `setConfig(nextConfig)` 更新表单，再 `await setConfig(nextConfig)`。回调只放在这次 bridge 调用成功之后、`setSettings` 之前，参数是 `nextConfig`。页面不得因为表单先变了就更新基线。
- bridge 方法、这三处的调用顺序、`try/catch` 和错误文案保持不变。除这四个配置 hook 以及第 10 节第 11 条涉及的 `useRecorderDashboardSnapshot.ts` 外，其他 hook 不改。第 10 节第 7、8 条必须从 `RecorderPage` 经这两条上层 hook 打到命令 hook。直接调用命令 hook 不算通过。
- `RecorderPage` 把回调接到基线。`handleApplyConfig` 的成功分支不再自己猜提交结果。它仍然只在 `status: 'success'` 时显示成功，因为这个函数会吞掉错误并返回 `Promise<void>`。

保存进行中禁用保存和放弃。回调里的副本是提交当时的配置。请求未完成时用户又改了表单，基线等于回调副本，不等于最新的 `config`。两边还有差异时，未保存项数继续显示。

底部栏文案为「有 N 项未保存」。最后一项距离保存栏至少留出栏的高度，1080×760 下滚到末项时不被挡住。保存仍调用现有 `handleApplyConfig()`。

## 10. 行为护栏

测试渲染页面或已抽出的处理器，向一个桩对象记录 `window.reqcaseShadowRecorder` 的调用。断言次数和参数。不读取源码字符串来判断行为。桩不用 `main.tsx` 里的演示桥，那个桥对导出和截图会抛错。

页面处理器和 preload 方法不是同名。测试断言右边这一列：

| 用户动作 | 页面处理器 | bridge 方法 |
|---|---|---|
| 开始 | `handleStart` → `runtime.startRecording` | 先 `setConfig(当前 config)`，再 `start()` |
| 暂停 | `handleRecPillClick` → `runtime.pauseRecording` | `pause()` |
| 继续 | `handleRecPillClick` → `runtime.resumeRecording` | `resume()` |
| 停止 | `handleStop` → `runtime.stopRecording` | `stop()` |
| 保存配置 | `handleApplyConfig` → `runtime.applyConfig` | `setConfig(提交副本)` |
| 应用预设 | `tuning.applyProfile` | `setConfig(nextConfig)`，然后 `setSettings(...)` |
| 删除会话 | `dashboard.deleteSessions` | `deleteTestSession({ sessionIds })` |
| 导出 | `handleExportCurrentSession` 或回顾页 `exportSession` | `exportTestSessionEvidence`，其中 `range.startMs`、`range.endMs` 是毫秒 |
| 标记缺陷 | 工作台或 `RecordingReviewPanel` | `markTestDefect`，包含 `sessionId` |
| 唤起悬浮岛 | 顶栏按钮 → `handleHideToTray` | `hideToTray()` |

至少这些用例：

1. 未录制时点开始：`setConfig` 1 次，参数等于当时配置；`start` 1 次。不调用 `pause`。
2. 录制中点录制按钮：`pause` 1 次。不调用 `start` 或 `stop`。
3. 暂停时点录制按钮：`resume` 1 次。
4. 录制中点停止：`stop` 1 次。录制按钮不可代替这次点击。
5. 保存成功：`setConfig` 的参数等于提交副本，未保存项数变为 0。保存期间又改过的字段仍计为未保存。
6. `setConfig` 拒绝：不调用 `onConfigCommitted`，出现现有错误反馈，基线与保存前相同。
7. 配置已写入但开始失败：`setConfig` 成功后回调 1 次，参数等于提交副本；随后 `start()` 拒绝。基线等于该副本，不回滚。
8. 配置已写入但设置保存失败：`applyProfile` 里 bridge 的 `setConfig` 成功后回调 1 次，参数等于 `nextConfig`；随后 `setSettings` 拒绝，现有 `onError` 仍被调用。基线等于 `nextConfig`。表单在 bridge 写入前已经更新，这不构成基线更新。
9. 选择模式下取消或退出：不调用 `deleteTestSession`。
10. 确认删除：`sessionIds` 等于当时选中的 ID，不受筛选隐藏的影响。
11. 返回 `{ deleted, skipped }` 且 `skipped` 非空：不退出选择模式，跳过的 ID 仍选中且在会话列表中可见。提示同时包含删除数和跳过数。全部成功才清空选择并退出选择模式。（注：`useRecorderDashboardSnapshot.ts` 的 `deleteSessions` 在乐观调用 `forgetSessions` 后恢复 `skipped` 时，必须重置 `snapshotSignatureRef.current = ''` 并在存在 `inFlightRefreshRef.current` 时补跑一次最新 `refresh()`，否则签名未变会导致 `refresh()` 提前返回、被跳过的会话无法回到 `sessions`；同时 `RecorderPage.tsx` 在删除返回后显式用 `skipped` 回填 `historySelection`，防止等待期间被 `useEffect` 清空。）
12. 导出选区：`range.startMs` 和 `range.endMs` 与 `export-range.ts` 算出的毫秒墙钟一致，不能把秒乘错或漏乘 1000。
13. 导出进度 `canceled` 和 `failed`：各出现一次对应语气的 `showToast`，不把取消显示成成功。

| 阶段 | 工作日 | 依赖 |
|---|---|---|

32–39 天由阶段表逐项相加得到：最短 3+3+3+5+6+8+3+1，最长 4+4+3+6+7+10+3+2。各阶段里的 Windows 冒烟算在这 32–39 天里。返修另加 5 个工作日，得到 37–44 天。对外排期按 8–9 周。不再把 7–8 周和这一周返修同时承诺。P3 与 P4 不并行。P6 可以放在 P1 之后的空隙，只要生成脚本已经存在。
