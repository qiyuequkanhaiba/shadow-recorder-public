# 测试会话循环录制与事件时间线技术设计

## 1. 文档目的

本文档用于将“测试会话循环录制与事件时间线”方案修订为与当前仓库实际一致的可执行版本。

本次修订重点：

- 明确当前项目实际技术栈是 `Rust + NAPI-RS + Electron + React`，不是 `Tauri`。
- 以现有能力为基础设计增量方案，而不是按全新产品重写。
- 明确最终主目标是“循环视频记录桌面操作 + 视频回放 + 事件侧带”，而不是前端按图片时间线排布回放。
- 支持扩展显示器，将多显示器采集和回放作为主线能力设计，而不是后补。
- 给出分阶段实施计划、验收标准和执行清单，便于直接进入开发。
- 自 `2026-04` 起，放弃 `windows-record` 替换路线，改为采用更接近 `Windrecorder` 的“`FFmpeg helper + 本地分段视频 + 侧带事件日志`”重构方向。

## 2. 当前项目实际情况

### 2.1 实际技术栈

当前仓库由两部分组成：

- Rust 原生插件：`NAPI-RS` 导出接口，负责 Windows 输入事件与窗口画面采集。
- 桌面宿主示例：`Electron + React + TypeScript`，负责 IPC、配置、时间线展示和报告导出。

### 2.2 现有能力

当前已经具备以下基础能力：

- 基于 `WH_MOUSE_LL` 和 `Raw Input` 的鼠标点击类事件采集。
- `DXGI` / `WGC` 双后端窗口画面采集，支持回退与上下文复用。
- `dirty rect` / `hash dedup` / 自适应质量策略。
- 基于 `StepData` 的内存环形缓冲，支持分页读取、按需取图、push/poll 两种消费模式。
- 已具备内部录像会话生命周期：
  - 底层 Rust / NAPI 结构体仍沿用 `TestSession` 命名，但主产品面已不再单独暴露“测试会话”操作。
  - 开始
  - 暂停
  - 恢复
  - 停止
- 已具备结构化事件时间线持久化：
  - `session.json`
  - `events.ndjson`
  - `artifacts/` 步骤快照
- 已接入会话事件类型：
  - 生命周期事件
  - `step_captured`
  - 人工备注
  - 应用日志
  - 窗口系统事件
  - 剪贴板事件
- 已接入 `WinEventHook` 事件：
  - 前台切换
  - 焦点变化
  - 显示
  - 隐藏
  - 标题变化
- 已为 `focus/show/hide` 增加基础去噪，避免同窗口短时间重复刷屏。
- React 已提供录像日志与回放面板：
  - 最近录像切换
  - 日志分类筛选
  - 事件详情
  - 视频回放定位
- Electron 示例中已保留主链路相关能力：
  - 悬浮窗
  - 托盘
  - 视频回放
  - 证据导出
- Rust 侧已有基础单元测试，当前核心测试可通过。

### 2.3 当前能力边界

当前实现仍然明显缺少以下能力：

- 还没有持续的循环视频环形缓冲；当前只有步骤触发型快照持久化，没有 `snapshot_segment`，更没有 `video_segment`。
- 会话的 `target_pid` / `target_hwnd` / `target_capture_mode` 目前主要是元数据落盘，还没有真正驱动 `DXGI/WGC` 绑定目标窗口。
- 历史会话列表目前主要是当前进程内最近记录，没有“跨重启自动扫描会话目录并建立索引”的能力。
- 还没有 `StepBuilder`，时间线事件尚未聚合成更稳定的 `StepRecord` 语义步骤。
- 还没有异常冻结、`IncidentCase`、事故目录和标准证据包导出。
- 还没有键盘摘要、UIA 补全和更高层的步骤语义增强。
- `WinEventHook/Clipboard` 的人工噪音校准仍需继续。
- 虽然已经补了真实桌面长时 smoke test，但仍需要继续扩大多显示器和更长时长覆盖。

### 2.4 与原文不符的点

原文中以下假设与仓库现状不符，需修正：

- 原文假设后端是 `src-tauri/src/services/`，实际应落在 Rust 插件 `src/` 与 Electron 模块层。
- 原文假设已有“本地存储、日志、设置、窗口管理与 Tauri command 基础”，实际现有公开控制面是 NAPI 导出和 Electron IPC。
- 原文直接要求“循环视频缓冲”，但当前仓库没有视频编码依赖，也没有分片写入链路。

## 3. 目标与非目标

### 3.1 目标

- 在测试会话期间持续记录测试人员关键操作。
- 在偶现问题发生时，保留异常前后足够完整的证据。
- 输出结果兼具可回看性、可检索性和可导出性。
- 以前端视频播放器作为主回放形态，系统事件、操作事件和步骤作为同步元数据叠加。
- 支持单显示器和扩展显示器场景下的持续录制、冻结和回放。
- 在当前代码基础上增量实现，避免推翻现有 Rust 采集底座与 Electron 示例。
- 将资源消耗控制在办公测试机可长期运行范围内。

### 3.2 非目标

- 不在第一阶段追求全桌面高帧率长期录屏。
- 不默认持久化所有原始键鼠流。
- 不让 React / WebView 承担系统级采集主逻辑。
- 不在第一阶段同时完成真实视频编码、全量 UIA、自动异常识别和复杂回放编辑能力。

## 4. 设计原则

### 4.1 以现有底座为核心

现有 `DXGI/WGC + Hook/RawInput + StepData + RingBuffer + Metrics` 是成熟底座，应复用而不是替换。

### 4.2 会话优先，视频为主，事件为侧带

应先建立“测试会话、事件时间线、循环视频、步骤、事故包”的分层模型，再将现有 `StepData` 映射进去。

### 4.3 循环视频是主链路，快照仅作为降级或调试

考虑到当前仓库没有视频编码链路，实现上仍可保留抽象层，但产品目标应明确为“循环视频回放”：

- 主实现：`video_segment`，按时间切片保存可直接回放的视频片段。
- 降级实现：`snapshot_segment`，仅在编码器不可用、诊断模式或极端兼容场景下启用。

### 4.4 保持兼容

现有公开 API 与示例页面不应一次性废弃。应新增会话 API，同时保留现有 `start_recording` 等接口作为兼容模式或调试模式。

### 4.5 先视频主链路，再增强语义与质量

建议开发顺序：

1. 会话与时间线
2. 循环视频环形缓冲
3. 异常冻结与导出
4. UIA、键盘摘要、多显示器播放与质量增强

### 4.6 前端必须轻量、简洁、美观、高效

前端不应做成“重控制台 + 重表格 + 重卡片墙”的工具界面。

必须遵守以下原则：

- 主界面以视频播放器为中心，而不是以时间线图片列表为中心。
- 系统事件、操作事件、步骤列表都作为侧带信息，不抢主视觉。
- 默认信息密度克制，优先显示当前定位最需要的信息。
- 优先单层布局和清晰层级，避免嵌套过深的标签页、抽屉和卡片栈。
- 风格应简洁、专业、耐看，避免炫技动画和装饰性噪音。
- 所有高成本视图必须按需加载，保证界面响应快于“信息堆叠”。

## 5. 总体方案

### 5.1 目标架构

修订后的方案由五层组成：

1. `Session Runtime`
2. `Event Timeline`
3. `Video Ring`
4. `Step Builder`
5. `Incident Packager`

职责划分：

- `Session Runtime`
  负责测试会话生命周期、目标绑定、配置装配、线程协调。
- `Event Timeline`
  负责采集并标准化输入、窗口、剪贴板、日志等事件。
- `Video Ring`
  负责持续采样桌面或显示器画面、编码分段、淘汰、索引与按时间回取。
- `Step Builder`
  负责把时间线事件聚合为可读步骤。
- `Incident Packager`
  负责异常标记、冻结前后窗口证据、打包导出。

### 5.2 关键调整：循环视频作为主载体，事件时间线作为侧带

为了适配当前项目实际，底层仍保留抽象层，但产品和前端主形态应明确如下：

| 实现方式 | 适用阶段 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `video_segment` | Phase 2 主线 | 回放体验符合产品目标，前端播放器简单直接 | 需要新增编码器、容器、helper 进程或额外依赖 |
| `snapshot_segment` | 降级 / 调试 | 编码依赖少，适合作为故障兜底 | 不适合作为最终主回放形态 |

推荐路线：

- 直接以 `video_segment` 为主线实现。
- 保留 `snapshot_segment` 作为编码失败时的降级记录方式，而不是主产品形态。

### 5.3 目标工作模式

#### 非录制状态

- 不启动录像会话。
- 现有兼容录制接口仅作为调试/兼容模式保留。

#### 录制状态

- 启动内部录像会话上下文。
- 启动事件源。
- 启动循环视频环形缓冲。
- 启动步骤聚合器。
- 启动最小持久化写入。

#### 异常冻结状态

发生以下情况之一时进入冻结流程：

- 测试人员手动标记异常。
- 被测进程退出或关键窗口消失。
- 命中错误标题、错误日志关键字或预置规则。
- 自动化测试驱动层显式上报失败。

冻结结果应包含：

- 异常前 `N` 秒视频片段。
- 异常后 `M` 秒追加录制结果。
- 同时间范围内的事件。
- 同时间范围内的步骤。
- 关键截图、会话元数据、日志摘录。

建议默认值：

- `pre_freeze_window_seconds = 180`
- `post_freeze_window_seconds = 20`

### 5.4 多显示器工作模式

最终产品应支持扩展显示器，不应只围绕单窗口或单前台窗口设计。

建议支持三种采集模式：

- `target_window`
  仅采集目标窗口。
- `target_display`
  采集目标窗口所在显示器，适合桌面级回放。
- `all_displays`
  对所有显示器分别录制同步视频流。

多显示器第一版建议：

- 每个显示器独立生成一条视频流。
- 各流共享统一会话时钟。
- 事件按时间戳对齐到会话主时钟，不直接绑死单一视频文件。

原因：

- 扩展显示器存在负坐标和不同分辨率，当前 `DXGI` 路径已经有按显示器矩形和 `display_id` 工作的基础，更适合按显示器分流实现。
- 如果第一版就把所有显示器拼成一张超大虚拟桌面再编码，会明显放大编码、裁剪和播放器复杂度。

前端播放器建议：

- 主视图是视频播放器。
- 旁路视图是事件标记轨道和事件列表。
- 多显示器场景下支持：
  - 切换主显示器视频
  - 同步查看其他显示器视频缩略流
  - 根据事件 `display_id` 自动切换主播放器

## 8. 存储策略设计

## 8.1 推荐默认实现：文件目录 + NDJSON

结合当前仓库现状，第一版不建议立即引入复杂数据库。建议先采用：

- 会话目录
- `session.json`
- `events.ndjson`
- `steps.ndjson`
- `segments/*`
- `incidents/*`

目录建议：

```text
data/
  sessions/
    {session_id}/
      session.json
      events.ndjson
      steps.ndjson
      segments/
        seg-000001/
          manifest.json
          frames/
            000001.webp
            000002.webp
      incidents/
        {incident_id}/
          manifest.json
          timeline.ndjson
          steps.ndjson
          session.json
          visual/
          screenshots/
          logs/
```

原因：

- 与当前 Electron 报告导出模式一致。
- 不需要在第一阶段引入 SQLite 依赖与迁移脚本。
- 导出和调试都更直接。

## 8.2 索引策略

即使使用文件存储，也应维护最小索引：

- `session.json` 中记录会话配置与最新状态。
- `segments/index.json` 记录分段时间范围。
- `incidents/index.json` 记录事故包元数据。

## 8.3 后续可选升级：SQLite

当以下需求明确后，再考虑引入 SQLite：

- 大量历史会话检索。
- 跨会话统计查询。
- 多条件过滤和排序。
- 更强的数据一致性与恢复能力。

在此之前，文件存储更符合当前项目节奏。

## 9. 事件时间线设计

## 9.1 事件源分层

### 常驻事件源

- 鼠标点击类输入
  - 复用现有 Hook/RawInput。
- `SetWinEventHook`
  - 前台窗口切换
  - 焦点变化
  - 窗口显示/隐藏
  - 标题变化
- 剪贴板变更
  - `AddClipboardFormatListener`
- 应用自身日志
  - Electron 主进程关键操作
  - 自动化驱动上报的业务日志

### 条件性事件源

- 键盘摘要
- 拖拽开始/结束
- UIA 快照

### 默认不持久化事件

- 全量 `mousemove`
- 每个按键的按下/抬起原始流
- 全量滚轮连续轨迹
- 全量 UIA 树变化

## 9.2 鼠标事件接入策略

应继续复用现有输入自动切换策略：

- 默认 `InputMode::Auto`
- 优先 `RawInput`
- 发现丢包压力时切回 Hook

但要补一层统一事件标准化，输出 `TimelineEvent`，而不是直接把输入事件当最终步骤。

## 9.3 窗口事件接入策略

建议新增独立线程运行 `SetWinEventHook`，只采集低频高价值事件：

- `EVENT_SYSTEM_FOREGROUND`
- `EVENT_OBJECT_FOCUS`
- `EVENT_OBJECT_SHOW`
- `EVENT_OBJECT_HIDE`
- `EVENT_OBJECT_NAMECHANGE`
- 可选窗口移动/尺寸变化开始和结束

输出要求：

- 不阻塞主采集线程。
- 统一转为 `TimelineEvent`。
- 做去抖，避免窗口标题频繁变化刷屏。

## 9.4 剪贴板事件接入策略

建议采集：

- 时间戳
- 内容类型摘要

默认不直接保存剪贴板明文，只保存类型或摘要：

- `text`
- `image`
- `file_list`
- `html`

## 10. 循环视频与多显示器设计

## 10.1 目标绑定

当前 `DXGI/WGC` 的现有主路径仍偏向当前前台窗口采集。为了让测试会话真正支撑桌面视频录制，需新增“目标绑定 + 显示器绑定”策略：

- 会话启动时允许指定 `target_pid` / `target_hwnd` / `process_name`。
- 会话启动时允许指定 `display_id` 或 `all_displays`。
- 优先采集目标窗口。
- 若目标窗口暂不可用，再按配置选择：
  - 回退到前台窗口
  - 暂停视觉采集
  - 回退到所在显示器

默认建议：

- 第一版支持 `target_window`、`target_display`、`all_displays` 三种模式。

## 10.2 Phase 2 主实现：video segment

### 工作方式

- 独立采集线程持续拉取桌面或显示器帧。
- 每 `2 ~ 5` 秒生成一个视频 segment。
- 每个 segment 保存：
  - 视频文件
  - `manifest.json`
  - 首尾时间戳
  - `display_id`
  - 关键帧索引
- 仅保留最近 `buffer_window_seconds` 时间范围内的 segments。
- 多显示器模式下，每个 `display_id` 单独维护 segment 环。

### 建议参数

- `segment_duration_seconds = 2 ~ 5`
- `buffer_window_seconds = 180`
- `capture_fps = 8 ~ 15`
- `encoder_profile = low_latency`

### 优化策略

- 复用现有 `WGC/DXGI` 捕获上下文。
- 复用现有 `dirty rect` 和 `display_id` 信息，减少无效编码。
- 编码器建议放到 helper 进程或隔离线程，避免拖垮宿主。
- 无画面变化时允许降低实际编码帧率，但时间轴仍连续。

## 10.3 降级与调试：snapshot segment

仅在以下场景启用 `snapshot_segment`：

- 编码器不可用或硬件环境异常。
- 需要定位视频编码故障。
- 特殊调试场景只关心抽样画面。

## 10.4 资源预算

### Phase 2 Video Segment 预算

在 `8 ~ 15 fps`、显示器级采集下，目标预算：

- CPU：额外 `5% ~ 12%`
- 内存：额外 `150MB ~ 350MB`
- 磁盘：最近 3 分钟单显示器稳定在 `200MB ~ 800MB`

说明：

- 若启用 `all_displays`，磁盘和编码预算按显示器数量线性上升。
- 第一版应优先保证“能稳定回放”，其次再继续压缩占用。

### 已落地的默认告警阈值

当前实现已经在 `video_segment` 运行时内置默认预算监控，并通过 `video-budget` 应用日志与视频流状态暴露：

- 捕获延迟告警：
  - 当单次 `capture_latency_ms >= max(2 * sample_interval_ms, 500ms)` 时触发。
- 编码不可用告警：
  - 当前运行环境找不到内置或可用 `ffmpeg` 时触发，并退回 `webp_sequence`。
- 编码退化告警：
  - `ffmpeg` 可用但未成功产出可播放 `mp4/webm` segment 时触发。
- 编码耗时告警：
  - 单个 segment 的编码耗时大于等于 `segment_duration_seconds * 1000` 时触发。
- 单 segment 体积告警：
  - 单个 segment 大于等于 `64 MiB` 时触发。
- 保留窗口体积告警：
  - 单条视频流当前保留的 segment 总量大于等于 `256 MiB` 时触发。
- 告警节流：
  - 同一类预算告警默认 `15s` 内最多写一次，避免日志刷屏。

前端轻量播放器区域应直接显示以下预算摘要，而不再要求单独的大型监控面板：

- `playable/pending segment` 数量
- 当前保留体积
- 最近捕获延迟与编码延迟
- 编码器是否可用
- 当前流累计告警数与最后一条告警

### 多显示器回放策略

- 第一版不要求把多个显示器拼成单一视频文件。
- 采用“单播放器 + 同步副流/切换”的 UI 方案即可满足回放和定位需求。
- 事件列表中的 `display_id` 应成为播放器切换依据。

## 11. 步骤生成设计

## 11.1 目标

将原始事件流转为测试人员和开发人员都能快速理解的步骤文本。

## 11.2 典型输出

## 11.4 UIA 策略

UIA 不做主链路，不做全程高频监听，仅在以下场景补充：

- 鼠标点击
- 焦点变化
- 前台窗口切换
- 标记异常

- `Name`
- `AutomationId`
- `ControlType`
- `ClassName`
- `FrameworkId`
- `BoundingRectangle`
- `IsEnabled`
- 可选 `ValuePattern` 摘要

要求：

- UIA 查询在独立线程运行。
- 设置超时，超时即放弃。
- 失败时不影响主录制链路。

## 11.5 隐私策略

对可能包含敏感信息的输入与控件值：

- 记录字段身份。
- 不记录明文。
- 只记录长度、类型或掩码。

例如：

- 在“密码”输入框输入 8 个字符

## 12. 异常冻结与事故包设计

## 12.1 触发方式

### 手动触发

### 自动触发

- 目标关键窗口消失
- 命中错误标题

## 12.2 冻结流程

1. 锁定当前会话状态。
2. 截取异常前 `N` 秒的 segment、event、step。
3. 继续采集异常后 `M` 秒。
4. 生成事故目录与 manifest。
5. 更新会话中的 incident 索引。

## 12.3 事故包结构

- `manifest.json`
- `session.json`
- `timeline.ndjson`
- `steps.ndjson`
- `visual/`
- `screenshots/`
- `logs/`
- `summary.json`

当前 `report-export.ts` 可以继续作为“人类可读导出”层复用，但不应直接承担事故包结构定义。

建议关系：

  负责标准证据包。

## 13.4 前端体验与视觉约束

### 布局原则

- 单窗口内优先采用“三段式轻布局”：
  - 顶部窄工具栏
  - 中央主播放器区
  - 右侧或下方可折叠事件侧栏
- 默认只展开一个主任务区，避免多个同级大面板同时争抢注意力。
- 多显示器场景下，副显示器视频默认以缩略条或切换器呈现，不默认并排堆满全屏。

### 交互原则

- 常用操作收敛为少量主按钮：
  - 开始会话
  - 停止会话
  - 标记异常
  - 导出
- 事件筛选应轻量，不做复杂查询构建器作为首屏默认交互。
- 点击事件后应直接驱动播放器跳转，而不是打开新的复杂详情流。
- 支持键盘快捷键和基础无障碍焦点流转。

### 性能原则

- 视频播放器是唯一主重组件，其余列表和详情面板必须轻量。
- 事件列表、步骤列表、事故列表应支持虚拟化或分页。
- 事件详情、截图、附属视频、事故材料一律懒加载。
- 不在 renderer 中做重编码、重拼帧、长时间阻塞计算。

### 视觉原则

- 采用克制、专业、低噪音的视觉语言。
- 控件尺寸、留白和对齐要服务于“快速定位问题”，而不是展示组件数量。
- 强调色只用于：
  - 当前录制状态
  - 异常标记
  - 当前选中事件
- 动效只用于状态切换和定位反馈，不做持续吸引注意力的装饰动画。

### 应避免的反模式

- 默认打开多个高密度面板。
- 以长图流或瀑布流方式回看操作。
- 为每类事件都单独做大卡片。
- 让筛选器、统计卡和配置项占据主首屏。
- 因图片预览、事件详情或样式装饰导致播放器区域被压缩。

## 17. 风险与应对

## 17.1 真实视频分片复杂度高

风险：

- 当前仓库没有视频编码链路。
- 一次性引入真实视频会放大复杂度与不稳定性。

应对：

- 以 `video_segment` 为主线，但从一开始就按 helper 进程或隔离编码线程设计。
- 保留 `snapshot_segment` 作为编码失败时的降级兜底，而不是替代主线。

## 17.2 主宿主崩溃导致证据丢失

风险：

- 目前录制链路与宿主进程耦合较紧。

应对：

- 将会话运行时尽量放在 Rust 独立线程。
- 事故包导出可放 Electron utility process。
- Phase 2 起就优先采用 helper 进程或隔离编码线程。

## 17.3 UIA 不稳定

风险：

- 某些目标应用控件树残缺或调用很慢。

应对：

- UIA 只做补充，不做主链路依赖。
- 设置超时，失败即降级。

## 17.4 数据隐私

风险：

- 输入内容、截图、剪贴板可能包含敏感数据。

应对：

- 默认脱敏。
- 支持排除进程与窗口。
- 事故包导出前提供再次脱敏选项。

## 17.5 存储膨胀

风险：

- 视频 segment 在多显示器下磁盘占用仍可能较高。

应对：

- 强制 segment 数量上限。
- 默认中低帧率与短 segment。
- 多显示器分流而不是拼接超大画布。
- 复用 dedup / dirty rect。
- 编码参数按显示器数量动态收敛。

## 18. 最终建议

结合当前项目实际，最合理的主线方案应直接围绕“循环视频 + 事件侧带”展开：

`测试会话模型 + 结构化事件时间线 + 循环视频环形缓冲 + 步骤生成 + 异常冻结导出`

其中：

- 第一阶段的视频证据主链路应直接采用 `video_segment`。
- `snapshot_segment` 只保留为编码失败时的降级项。
- 存储应先采用目录 + NDJSON + manifest 的轻量方案。
- 会话控制、导出、UI 应继续建立在当前 NAPI + Electron IPC 基础上。
- 前端主回放形态应是视频播放器，而不是图片时间线排布。

建议立即执行的开发顺序：

1. Phase 0：模块骨架与模型定义
2. Phase 1：会话与事件时间线
3. Phase 2：循环视频环形缓冲
4. Phase 3：步骤生成与异常冻结
5. Phase 4：UIA、多显示器播放与质量增强

## 19. 已放弃：基于 `windows-record` 替换当前视频录制内核方案

### 19.1 目标

本节用于将当前仓库中自研的连续视频采集主链路，替换为基于 `windows-record` 的视频录制内核。

替换目标仅限“连续视频录制与回放片段生成”这一层，不推翻以下既有能力：

- Rust `SessionManager`、事件模型与 `events.ndjson`
- Electron IPC 与 NAPI 接口层
- React 主窗口、日志窗口、导出入口
- 证据包目录结构与导出逻辑
- 步骤级快照与事件时间线

### 19.2 采用原因

相对当前仓库中 `video_segment.rs` 自建采样 + JPEG 帧序列 + ffmpeg 再编码方案，`windows-record` 更适合作为底层视频录制内核，原因如下：

- 它本身就是 Rust 录制库，和当前 `Rust + NAPI` 架构兼容，不需要再引入一套新的 Node 原生桥。
- 它直接面向 Windows 录制主场景，目标和当前产品更一致。
- 它天然更适合做“连续视频录制 + 回放缓冲”，比当前“截图序列再转视频”的链路稳定。
- 它可以显著减少当前 stop/finalize/补帧/拼接链路的复杂度。

### 19.3 不直接采用 `@getexcited/chompers` 的原因

`@getexcited/chompers` 可以作为参考，但不建议直接接入当前主产品，原因如下：

- 它本质上是另一层 Node/Electron 原生封装，会与当前仓库已有 `native-binding.ts + Rust NAPI` 结构重叠。
- 当前项目已经有完整的会话、事件、导出、前端链路，直接换成 `chompers` 会增加桥接迁移成本。
- `chompers` 更适合快速 PoC，不适合作为当前主仓库的直接替代方案。

因此推荐策略是：

- 录制内核：引入 `windows-record`
- 业务层：保留当前仓库结构
- 外层接口：维持当前 NAPI / Electron / React 不变

### 19.4 替换边界

替换后，新的职责划分应如下：

- `windows-record`
  - 连续视频录制
  - 回放缓冲
  - 多显示器视频流
  - 窗口/桌面录制主链路
- 当前仓库自有逻辑
  - 测试会话生命周期
  - 事件采集与持久化
  - 日志分类/过滤
  - 视频与事件的时间戳映射
  - 主窗口回放界面
  - 证据导出

不应继续由当前仓库自建的能力：

- 运行中的重复补帧
- JPEG 帧序列到 `mp4` 的主录制链
- 停止录制时同步恢复 segment 与补尾帧
- 多段 `ffmpeg concat` 作为主回放方案

### 19.5 建议的替换架构

#### 19.5.1 Rust 层

新增独立模块：

- `src/session/windows_record_runtime.rs`
- `src/session/windows_record_types.rs`
- `src/session/windows_record_adapter.rs`

职责：

- 封装 `windows-record` 的 recorder 生命周期
- 将 `foreground_window / desktop / target_display / all_displays` 转换为对应录制目标
- 将 `windows-record` 输出转换成当前仓库可用的 `TestSessionVideoStreamRecord / TestSessionVideoSegmentRecord`
- 在停止时仅做“快速 stop + flush 标记”，不在主线程阻塞等待复杂补救逻辑

保留模块：

- `src/session/manager.rs`
- `src/session/models.rs`
- `src/session/system_events.rs`
- `src/lib.rs`

降级模块：

- `src/session/video_segment.rs`

处理方式：

- 第一阶段保留文件，但从“主实现”降级为“legacy fallback”
- 新实现稳定后，再物理删除或仅保留测试辅助逻辑

#### 19.5.2 Electron / React 层

Electron 与 React 不应直接感知 `windows-record`，只认当前会话与视频流 DTO。

也就是说，以下文件应尽量保持接口兼容：

- `examples/desktop/src-electron/native-binding.ts`

- 增加 `finalizing` / `ready` / `error` 状态展示
- 改为优先回放单个连续视频文件或 `windows-record` 产物
- 去掉对旧 JPEG 帧序列的依赖

### 19.6 目标模式映射

`windows-record` 接入后，录制目标的处理建议如下：

- `foreground_window`
  - 监控前台窗口变化
  - 当 `hwnd` 改变时切换录制目标
  - 事件时间线继续记录窗口切换
- `desktop`
  - 录制主桌面或主显示器
- `target_display`
  - 录制指定显示器
- `all_displays`
  - 每个显示器一条独立视频流

不建议：

- 将多显示器拼成一个超大画布作为单视频主方案

建议：

- 多显示器保持“一显示器一视频流”
- 前端按流切换回放
- 导出时保留多流目录结构

### 19.7 停止录制路径重构要求

当前 stop 卡死问题说明旧链路存在结构性问题，因此切换到 `windows-record` 时，必须同步重构 stop 语义：

- “停止录制”只负责发出 stop 信号并快速返回
- “最终整理视频文件 / 索引 / manifest”应放到后台 finalize 流程
- 前端状态应区分：
  - `recording`
  - `stopping`
  - `finalizing`
  - `ready`
- 主窗口在 `finalizing` 阶段允许继续查看事件日志，不阻塞整个 UI

### 19.8 数据落盘建议

建议保持当前仓库的目录组织，不因更换录制内核而推翻导出结构：

- `session.json`
- `events.ndjson`
- `video/streams.json`
- `video/segments.ndjson`
- `video/streams/<streamId>/...`

变化点：

- `segment.mp4 / segment.webm` 应优先直接来自 `windows-record`
- `frames/` 目录不再作为主回放依赖
- 仅在 debug 或 fallback 模式下保留原始帧序列

## 20. 2026-04 重构决议：基于 `Windrecorder` 思路重构录制链

### 20.1 决议

经对 `Screenpipe`、`Windrecorder` 和 `windows-record` 路线重新评估后，当前项目正式放弃“继续以自建帧采样编码链或 `windows-record` fork 作为主线”的方案，改为采用更接近 `Windrecorder` 的实现思路：

- 视频为主数据
- 事件为侧带日志
- `FFmpeg helper` 负责稳定分段录制
- Rust 负责会话、事件和索引
- Electron 负责托盘、悬浮窗、导出与进程控制
- React 只负责连续视频回放和日志过滤

### 20.2 为什么转向

当前仓库主链存在以下结构性问题：

- 自建 `video_segment.rs` 复杂度过高，stop/finalize 容易卡死。
- 前端已经多次暴露“只有首帧、不连续、停止卡死、播放闪烁”等问题。
- `windows-record` 在当前机器上虽然通过 WR-0.8 证明了 `memory sample` 路径可行，但它仍不具备可直接替换主工程的成熟度。

而 `Windrecorder` 的整体思路更贴近当前产品目标：

- 后台常驻
- 按时间窗口循环保留视频
- 以分段视频为主回放载体
- 事件和索引作为辅助定位层

### 20.3 新主方案

新的主方案定义为：

`FFmpeg Loop Runtime + Event Timeline + Session Index + Continuous Playback + Minimal Export`

产品面只保留四个核心能力：

1. 循环录制视频
2. 监测并记录系统/软件事件
3. 停止后立即连续回放
4. 导出视频与日志

明确不再作为主产品面的能力：

- `windows-record` 替换路线
- 前端图片时间线主回放
- 复杂卡片式事件浏览
- AI / benchmark / 模板化报告主入口

### 20.4 新的职责分层

#### Rust

- `SessionManager`
  - 会话生命周期
  - 流与 segment 元数据
  - `events.ndjson`
- `SystemEventRuntime`
  - `WinEventHook`
  - 剪贴板
  - 应用日志标准化
- `FfmpegLoopRuntime`
  - 启停 `ffmpeg` helper
  - 维护 segment 轮转与淘汰
  - 生成 `streams.json / segments.ndjson`

#### Electron

- 启动默认只显示悬浮窗
- 负责托盘、主窗口、导出
- 负责把打包内置 `ffmpeg.exe` 暴露给原生层

#### React

- 左侧：连续视频播放器
- 右侧：固定高度日志窗
- 设置页：录制时长、分段时长、目标显示器、全部显示器

### 20.5 Phase B 定义

Phase B 是本轮开始实施的新录制内核阶段，目标是先把“按时间循环保留的视频录制链”从当前自建帧采样主链中剥离出来。

#### Phase B 范围

- 新建 `ffmpeg_loop_runtime`
- 录制模式优先支持：
  - `desktop`
  - `target_display`
  - `all_displays`
  - `foreground_window`
- 录制开始后自动创建分段视频目录
- 停止录制后快速返回，不再做主线程上的大合并
- 从 `ffmpeg` 的 segment list 重建 `segments.ndjson`

#### Phase B 不做

- 不在本阶段解决窗口级精准跟随录制
- 不在本阶段重写前端播放器
- 不在本阶段完成更高层步骤语义聚合

2026-04-04 验证记录：

- `target_display` 真实桌面 smoke：`65s / 5s segment / 90s window`，产出 `13` 个可播放片段，累计约 `65000ms`，无 warning。
- `foreground_window` 真实桌面 smoke：`65s / 5s segment / 90s window`，产出 `14` 个可播放片段，累计约 `62200ms`，无 warning。
- 验证中确认旧的 `ffmpeg 1.0.1` 不支持 `gdigrab`，已为 runtime 增加 capability probe，启动时会直接给出明确告警。
- `prepare:ffmpeg` 已升级为自动准备现代版内置编码器：本地缺失或过旧时会自动下载并校验 `ffmpeg 8.1 essentials`，然后覆盖 `tools/ffmpeg/bin/ffmpeg.exe` 与 `build-resources/ffmpeg/bin/ffmpeg.exe`。
- 已新增编码专项 benchmark，支持按 `recordingProfile / encoderPreference` 矩阵跑真实录制，并输出 `encoding-benchmark.json/.md`，用于比较 `auto / hardware / software` 与 `efficiency / balanced / smooth` 的 CPU、内存和可播片段表现。

2026-04-06 编码专项 benchmark 基线结论：

- 当前验证机上 `auto / hardware / software` 最终都回退到 `ffmpeg:gdigrab-libx264`，说明暂未命中可用硬件编码器。
- `target_display` 下，`efficiency / balanced / smooth` 的 CPU 与内存差异不够大，不足以推翻当前 `balanced` 默认值。
- `foreground_window` 下，`balanced + auto` 与 `balanced + software` 都稳定，但整体 CPU / 内存明显低于 `target_display`。
- 因此当前默认推荐保持：
  - `recordingProfile = balanced`
  - `encoderPreference = auto`
- 后续若在目标机器上检测到稳定可用的 `nvenc/qsv/amf`，再单独更新默认推荐。

### 20.8 新的近期顺序

在本决议下，后续开发顺序改为：

1. Phase B：`ffmpeg loop runtime`
2. Phase C：事件日志侧带收口
3. Phase D：连续回放简化
4. Phase E：最小化导出

### 20.9 最终建议

从这一版开始，主工程应以 `Windrecorder-like` 路线为准：

- 用 `ffmpeg helper` 解决稳定视频录制
- 用结构化日志解决测试行为追踪
- 用简单播放器解决回放
- 用最小目录/ZIP 解决导出

后续所有实现都应优先服务这条主线，而不是继续扩展复杂试验性录制内核。
